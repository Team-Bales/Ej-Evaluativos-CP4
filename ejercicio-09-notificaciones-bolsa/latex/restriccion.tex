\begin{quote}
\itshape
El sistema debe garantizar entrega \emph{at-least-once} y persistir notificaciones fallidas.
\end{quote}

La entrega asíncrona del inciso~c aísla los fallos y reintenta, pero toda esa estructura vive
\textbf{en memoria}: si el proceso se cae, lo que estaba en vuelo se pierde. La restricción pide
dos cosas que se apoyan en la misma decisión de diseño: \textbf{escribir la notificación en un
almacén durable antes de intentar enviarla} (patrón \emph{outbox}) y \textbf{no borrar nada que
no se haya confirmado}. Con eso, un aviso que falló sigue en el disco y un aviso a medias se
recupera al reiniciar.

La implementación es real y está en el repositorio: repositorio persistente en archivo, estados
durables, recuperación al arrancar y siete pruebas que lo comprueban.

¿Cómo se garantiza \emph{at-least-once}? &

\subsubsection{El outbox: escribir antes de enviar}

El despacho del inciso~c ya tenía la forma correcta: \texttt{Encolar} no espera a ningún canal y
los consumidores envían en segundo plano. Lo que le faltaba era la \textbf{durabilidad}. La
solución es una capacidad opcional del repositorio, \texttt{IRepositorioOutbox}, que el
despachador detecta sin cambiar de contrato:

\begin{lstlisting}[basicstyle=\ttfamily\footnotesize, columns=fullflexible, keepspaces=true, caption={El despachador persiste antes de encolar (solo si el repositorio sabe hacerlo).}]
public void Encolar(Notificacion notificacion)
{
    // Outbox: la notificación queda en el disco ANTES de que se intente enviar.
    _outbox?.RegistrarPendiente(notificacion, intentos: 0);

    Interlocked.Increment(ref _enProceso);
    if (_cola.Writer.TryWrite(new EnvioPendiente(notificacion, Intentos: 0)))
    {
        return;
    }
    // ... cola llena: el aviso sigue pendiente en el outbox, no se pierde.
}
\end{lstlisting}

La línea que decide todo es la primera: entre \texttt{RegistrarPendiente} y \texttt{TryWrite} hay
una ventana en la que el aviso \textbf{ya está en el disco y todavía no se ha enviado}. Si el
proceso muere ahí, el aviso se recupera al siguiente arranque. Ese es el sentido de
\emph{at-least-once}: la entrega ocurre \emph{al menos una vez}, y el precio de esa garantía es que
puede ocurrir dos veces.

\subsubsection{Idempotencia}

Un aviso reenviado no puede crear una segunda fila. La clave es el \texttt{Id} de la
\texttt{Notificacion}, que se genera al crearla y viaja con ella por todo el flujo:

\begin{lstlisting}[basicstyle=\ttfamily\footnotesize, columns=fullflexible, keepspaces=true, caption={El registro es un \emph{upsert} por \texttt{Id}: reenviar no duplica.}]
private void Upsert(RegistroOutbox registro)
{
    if (!_registros.ContainsKey(registro.Id))
    {
        _orden.Add(registro.Id);
    }

    _registros[registro.Id] = registro;
    Volcar();
}
\end{lstlisting}

Y al registrar un aviso que ya estaba entregado, el repositorio no lo reabre:

\begin{lstlisting}[basicstyle=\ttfamily\footnotesize, columns=fullflexible, keepspaces=true]
public void RegistrarPendiente(Notificacion notificacion, int intentos)
{
    RegistroOutbox? existente = Buscar(notificacion.Id);

    // Idempotencia: un aviso ya entregado no se vuelve a abrir. Si el mismo
    // Id llega otra vez, es un reenvío, no una notificación nueva.
    if (existente is not null && existente.Estado == EstadoNotificacion.Entregada)
    {
        return;
    }
    // ...
}
\end{lstlisting}

\subsubsection{Reintentos con backoff y \emph{dead letter} persistido}

El backoff del inciso~c se conserva intacto; lo que se añade es que cada desenlace queda
escrito:

\begin{lstlisting}[basicstyle=\ttfamily\footnotesize, columns=fullflexible, keepspaces=true, caption={Los tres desenlaces del envío, y lo que queda en el outbox.}]
// El canal confirma:
_repositorio.Guardar(envio.Notificacion);
_outbox?.MarcarEntregada(envio.Notificacion.Id);

// El canal falla y quedan intentos:
_outbox?.MarcarReintento(envio.Notificacion.Id, intentos, error.Message);
Reprogramar(envio with { Intentos = intentos });

// Se agotaron los intentos: dead letter, no se borra.
DarPorPerdida(envio.Notificacion, intentos, error.Message);
\end{lstlisting}

El contador de intentos \textbf{vive en el outbox}, no en la cola: por eso un reinicio no reinicia
la cuenta. Un aviso que ya falló dos veces y se recupera al tercer intento sigue llevando
\texttt{intentos = 2} después de la caída.

\subsubsection{Reinicio y recuperación}

Al arrancar, el proceso abre el outbox y devuelve a la cola lo que quedó pendiente:

\begin{lstlisting}[basicstyle=\ttfamily\footnotesize, columns=fullflexible, keepspaces=true, caption={Recuperar lo pendiente y reencolarlo con su contador de intentos.}]
public int RecuperarPendientes()
{
    IReadOnlyList<EnvioPendiente> pendientes = _outbox.PendientesParaReintentar();
    int recuperadas = 0;

    foreach (EnvioPendiente envio in pendientes)
    {
        if (_cola.Writer.TryWrite(envio))
        {
            Interlocked.Increment(ref _enProceso);
            recuperadas++;
        }
    }

    return recuperadas;
}
\end{lstlisting}

Un detalle que no es trivial: \textbf{el canal no se serializa}. Lo que se guarda en el archivo es
el \emph{tipo} del canal (por ejemplo \texttt{CanalEmail}), y al recuperar el aviso se reconstruye
con una fábrica:

\begin{lstlisting}[basicstyle=\ttfamily\footnotesize, columns=fullflexible, keepspaces=true]
public sealed class FabricaCanales : IFabricaCanales
{
    public ICanalNotificacion? Crear(string tipoCanal) => tipoCanal switch
    {
        nameof(CanalEmail) => new CanalEmail(),
        nameof(CanalSms)    => new CanalSms(),
        nameof(CanalPush)   => new CanalPush(),
        _ => null,   // tipo desconocido: el aviso no se pierde, queda pendiente
    };
}
\end{lstlisting}

Si el tipo no se puede reconstruir, el aviso \textbf{no se descarta}: sigue pendiente en el
outbox y queda listado en \texttt{NoRecuperables} para que un operador lo resuelva.

\subsubsection{Dónde vive la persistencia}

En este ejercicio, en un archivo JSON con reemplazo atómico: se escribe a un archivo temporal y
se renombra, para que un corte a mitad de guardado no deje el outbox a medias.

\begin{lstlisting}[basicstyle=\ttfamily\footnotesize, columns=fullflexible, keepspaces=true, caption={La escritura al disco es atómica: temporal y renombrado.}]
private void Volcar()
{
    string temporal = _ruta + ".tmp";
    File.WriteAllText(temporal, json);
    File.Move(temporal, _ruta, overwrite: true);
}
\end{lstlisting}

Si el archivo está dañado, el repositorio \textbf{falla en voz alta} en vez de continuar como si
el outbox estuviera vacío: un archivo corrupto significa notificaciones perdidas en silencio, y
eso es justo lo que la restricción quiere evitar.

\subsubsection{Límites del diseño}

Conviene ser explícito sobre lo que esta solución \emph{no} resuelve:

\begin{itemize}
  \item \textbf{Un solo proceso escritor.} Dos instancias sobre el mismo archivo se pisan, porque
        cada una mantiene su propia copia en memoria. En producción esto se resuelve con un
        \emph{outbox} transaccional en una base de datos, donde la escritura del aviso y la del
        evento de negocio van en la misma transacción.
  \item \textbf{No es exactly-once.} La garantía es \emph{at-least-once}: el cliente puede recibir
        dos avisos si el proceso se cae entre la confirmación del canal y la escritura del estado.
        Para evitarlo harían falta claves de idempotencia del lado del proveedor.
  \item \textbf{El outbox no sustituye al proveedor.} Si la dirección de correo ya no existe, el
        aviso se reintenta, agota los intentos y queda en \emph{dead letter}: la persistencia
        garantiza que la \emph{notificación} no se pierde, no que el \emph{cliente} la reciba.
\end{itemize}

La demostración usa el código real (\texttt{dotnet run --project Bolsa.Notificaciones --

  1) Entrega normal: la alerta persiste el aviso y el canal lo confirma.
[EMAIL → cliente0001@correo.cu] AAPL subió por encima de su umbral 151.00: 150.00 → 155.00
  → Outbox: cliente0001@correo.cu → Entregada (intentos: 0)

  2) Canal caído: se reintenta con backoff y, al agotar los intentos, queda en dead letter.
[FALLO DespachadorAsincrono] intento 1/2 del aviso de +53 50000009 (InvalidOperationException: ...)
[FALLO DespachadorAsincrono] intento 2/2 del aviso de +53 50000009 (InvalidOperationException: ...)
  → Outbox: +53 50000009 → FalloDefinitivo (intentos: 2)
     último error: El proveedor rechazó el aviso de +53 50000009

  3) El proceso se cae con el aviso ya persistido y sin enviar.
  → Outbox antes de la caída: cliente0002@correo.cu → Pendiente (intentos: 0)
  [CAÍDA] el proceso se detiene.

  --- Reinicio: otro proceso abre el mismo archivo ---
  Pendientes leídos del disco: 1
  Avisos recuperados por el despachador: 1
[EMAIL → cliente0002@correo.cu] AAPL subió por encima de su umbral 151.00: 150.00 → 155.00
  → Outbox: cliente0002@correo.cu → Entregada (intentos: 0)

  4) Idempotencia: el mismo aviso encolado dos veces deja una sola fila en el outbox.
[EMAIL → cliente0003@correo.cu] AAPL 151.00 → 155.00
[EMAIL → cliente0003@correo.cu] AAPL 151.00 → 155.00
  → Filas del outbox: 3 antes, 4 después.
     Filas con ese mismo Id: 1 (el reenvío no duplica el registro).

  --- Resumen del outbox ---
     Entregadas: 3   Pendientes: 0   Fallo definitivo: 1
\end{lstlisting}

La escena~3 es la importante: el aviso se entrega \emph{después} del reinicio, porque estaba en el
disco antes de que el proceso muriera. Y la escena~4 muestra el otro lado de la moneda: el cliente
puede recibir el aviso dos veces, pero el outbox guarda una sola fila.
